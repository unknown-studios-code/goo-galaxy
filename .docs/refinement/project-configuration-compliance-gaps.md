# Project configuration: rules the repository does not currently satisfy

> **Status:** raw problem description, not yet refined. Run `/refine-task` over this to produce the tech-task
> documents and the Notion pages. Nothing here is a decision — several of these are deliberately open, and at
> least one may be resolved by narrowing the rule rather than changing the project.
>
> This is almost certainly **more than one task**. The natural split is suggested at the end.

## How this was produced

A read-only audit of every Core Rule in `.claude/rules/unity-project-configuration.md` against the actual
repository, plus the configuration claims in `CLAUDE.md`. Every finding below was verified by opening the file
that holds the setting. Rules already resolved are listed at the bottom so nobody re-investigates them.

---

## 1. Build Profiles do not exist, yet CI builds on every PR

**Rule 8** — build configuration lives in Build Profile assets under `Assets/Settings/Build Profiles/`, one per
shipping target plus a development profile; never encode build settings in scripts.

**Actual state:** `Assets/Settings/Build Profiles/` does not exist. `Assets/Editor/Build/` contains only its
`.asmdef` — no build code either. Meanwhile `.github/workflows/unity-build-android.yml` and
`unity-build-ios.yml` run `game-ci/unity-builder` on **every pull request to `main`**, with no `buildMethod`
override, so the build falls back to whatever happens to be in `ProjectSettings/*.asset`.

**Why this is the highest-impact item:** this is not a future concern. The project already produces an Android
bundle and an iOS player from CI, from configuration nobody deliberately authored per target. There is no
development-vs-shipping split, no per-profile scene list, and nothing to diff when a build setting changes —
a regression in build configuration would land silently and only be visible in the artifact.

**Open questions for refinement:**

- Which targets need a profile now: Android + iOS shipping, plus one development profile? Or is a single
  development profile enough until there is something to ship?
- Should CI reference the profile by name, and should a missing profile fail the workflow rather than falling
  back to defaults?
- The scene list is currently empty of any real match scene (`Assets/Scenes/Bootstrap/Main.unity` is nearly
  empty; `Assets/Playtest/PlaytestScene.unity` is a throwaway harness). Deciding the scene list may have to
  wait for the real match bootstrap.

## 2. Managed stripping is unconfigured on an IL2CPP project that ships from CI

**Rule 9** — both mobile targets build with IL2CPP; keep the managed stripping level at the highest setting the
game still runs on, and preserve reflection-only types with a `link.xml`.

**Actual state:** `ProjectSettings/ProjectSettings.asset` has `managedStrippingLevel: {}` — an empty map, never
configured for any platform, so it silently rides the engine default. No `link.xml` exists anywhere in the
repository.

The rest of Rule 9 **is** satisfied and should not be re-litigated: `scriptingBackend: {Android: 1}` is IL2CPP,
and `AndroidTargetArchitectures: 2` is ARM64-only. iOS carries no explicit backend entry, which is expected —
Unity forces IL2CPP there regardless.

**Why it matters:** the rule's own text says stripping bugs "surface as `MissingMethodException` at runtime in a
build, never in the editor." Combined with finding #1 — real IL2CPP builds on every PR — there is nothing today
that would catch a reflection-only type being stripped before it reached a device. VContainer resolves through
reflection, so the DI container is the most likely first casualty.

**Open questions:** what stripping level to start at, and whether to add a `link.xml` pre-emptively for
VContainer or wait for the first failure.

## 3. No import presets at all

**Rule 5** — store import presets under `Assets/Settings/Presets/` (textures: Albedo, Normal, SingleSprite,
SpriteAtlas; audio: Music, Ambience, SFX, UI) and register them in the Preset Manager with folder or name
filters. "Never rely on a manually applied preset for content that ships."

**Actual state:** `Assets/Settings/Presets/` does not exist. `ProjectSettings/PresetManager.asset` has
`m_DefaultPresets: {}` — zero presets registered. Every import today is either configured by hand or left at
engine defaults.

**Why it matters:** this is cheap now and expensive later. The project has almost no art yet, so authoring the
presets costs little and every asset imported from here on is configured correctly on arrival. Once a few
hundred sprites are in, retrofitting means re-importing and re-verifying all of them.

**Note:** the two sprites currently in the repo (`Assets/Playtest/Prefabs/Sprite_Hex.png`, `Sprite_Blob.png`)
were generated by code with their importer settings applied programmatically — they are harness assets and are
not evidence either way.

## 4. URP has one pipeline asset and six stock quality levels — no tiers

**Rule 6** — one render pipeline asset per tier (Performant / Balanced / HighFidelity) under
`Assets/Settings/Rendering/`, with matching renderers and volume profiles. "Each tier must be a shippable
configuration on its target hardware, not a copy with one toggle changed."

**Actual state:**

- `Assets/Settings/Rendering/Pipeline/` holds a single `UniversalRP.asset`, plus `Renderer2D.asset`, plus
  `UniversalRenderPipelineGlobalSettings.asset`.
- `Assets/Settings/Profiles/Volume/` holds exactly one `DefaultVolumeProfile.asset`.
- `ProjectSettings/QualitySettings.asset` still carries Unity's stock six-level ladder — "Very Low / Low /
  Medium / High / Very High / Ultra" — and **every one of them points `customRenderPipeline` at the same GUID**,
  which is also the global pipeline in `GraphicsSettings.asset`.

So this is not a partially-built tier split; there are no tiers. Note that the current single-asset-everywhere
wiring is the result of a repair made during the GOOM-6 playtest work — the project had previously been running
the Built-in pipeline with the URP asset unassigned and its renderer field null. The wiring is now correct but
undifferentiated.

**Open questions:** whether three tiers are actually wanted for a 2D game, and what would meaningfully differ
between them. Rule 6 was written with a 3D pipeline in mind — for a 2D sprite game the tier axis may be
resolution scale, post-processing, and light count rather than shadows and depth textures. **This is a case
where amending the rule may be the right answer instead of building three tiers to satisfy it.**

## 5. `CLAUDE.md` claims a guardrail broader than what is enforced

**Rule 10 / CLAUDE.md Boundaries** — CLAUDE.md states: "Never write `.asset`, `.meta`, `.prefab`, or `.unity`
files directly… The `deny` rules in `.claude/settings.json` enforce this."

**Actual state:** the entire deny list is:

```json
"deny": ["Edit(Assets/**/*.meta)", "Edit(Assets/**/*.asset)"]
```

Three gaps against the written claim:

- `.prefab` and `.unity` are not denied at all.
- The pattern only covers `Assets/**`, so nothing under `ProjectSettings/` is denied — and that is exactly where
  the settings behind Rules 1, 4, 6, 8, and 9 live.
- Only the `Edit` tool is named. The `Write` tool, which creates new files rather than editing existing ones, is
  unrestricted for all four extensions.

**Why it matters:** the policy is documented as mechanically enforced when it is mostly convention. Anyone —
human or agent — reading CLAUDE.md would reasonably assume the guardrail catches mistakes it does not catch.

**Open question:** narrow the CLAUDE.md claim to what is actually enforced, or extend the deny list to `Write`
and to `.prefab` / `.unity` / `ProjectSettings/**`? Note that the MCP path is deliberately allowed now, so any
extension must not block the Unity MCP from authoring assets through the editor.

## 6. Nothing validates any of this

None of `format-check.yml`, `unity-tests-editmode.yml`, or `unity-tests-playmode.yml` asserts a single project
setting. Combined with finding #1 — builds already running on every PR — configuration drift has no detection
mechanism at all.

`Assets/Editor/Validation/` exists with an `.asmdef` and no code. A validation pass there, run in CI, could
assert the Enter Play Mode flags, the stripping level, the presence of Build Profiles, and the URP tier wiring
against the actual `ProjectSettings/*.asset` values.

**Open question:** is this worth building before the underlying items are fixed, or is it the thing that keeps
them fixed afterwards? Probably the latter, which makes it the last task in the sequence rather than the first.

## Not violations, but worth deciding

- **Rule 3 (Auto Refresh) — cannot be verified or enforced from the repository.** The rule points at
  Edit → Preferences → Asset Pipeline, which is a **per-user Editor Preference** stored in the OS registry, not
  in any tracked file. `ProjectSettings/EditorSettings.asset` does have `m_RefreshImportMode: 0`, but that field
  controls parallel-vs-sequential import during a refresh — it is not this setting. The rule is therefore
  unenforceable by construction. Consider marking it explicitly as a per-developer convention so nobody audits
  for it again. The same applies to the Burst "Enable Compilation" / "Synchronous Compilation" toggles in
  Rule 4, which live under the Jobs menu as session-scoped preferences.
- **Rule 4 (Burst) — not yet applicable.** No `BurstAotSettings_*.json` exists, `com.unity.burst` is only a
  transitive dependency, and grepping `Assets/Scripts/**` for `BurstCompile`, `IJob`, `Unity.Jobs`, and
  `Unity.Burst` returns nothing. There is nothing Burst-compiled for the rule to govern. It becomes applicable
  the moment the first job or `[BurstCompile]` method lands.
- **`Runtime.Networking` references `Runtime.Board` directly.** Rule 7 sanctions features referencing
  `Runtime.Shared`, and says nothing about feature-to-feature edges. `Networking` currently contains only its
  `AssemblyInfo.cs`, so this is unexercised scaffolding rather than an active violation — but
  `unity-netcode.md` suggests wire contracts belong in `Runtime.Shared`, which would make the edge unnecessary.
  Worth resolving before networking code lands, and worth a sentence in Rule 7 either way.
- **No rule pins test assembly naming.** Rule 7 defines `GooGalaxy.Runtime.{Feature}` and
  `GooGalaxy.Editor.{Domain}` but is silent on tests, which are neither. The two test assemblies are now
  consistent with each other (`GooGalaxy.Tests.EditMode` / `GooGalaxy.Tests.PlayMode`) after a rename, but
  nothing stops the next one from drifting. One line in Rule 7 would close it.

## Already resolved — do not re-investigate

- **Rule 1 (Enter Play Mode Options)** — was `m_EnterPlayModeOptionsEnabled: 1` with `m_EnterPlayModeOptions: 0`
  (i.e. the master toggle on but neither reload actually disabled). Configured manually by the user.
- **Rule 7, `Runtime.Shared` dependency** — the asmdef listed `"references": ["VContainer"]` despite no file in
  `Shared/` using VContainer or `[Inject]`, breaching the "dependency-free leaf" boundary that CLAUDE.md names.
  Reference removed; `references` is now empty.
- **Rule 2 (Static State Reset)** — verified compliant. The only mutable static state in the codebase is
  `MatchEvents`' seven static events, and `ResetEvents()` clears all of them from a
  `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` hook. Everything else static is `static readonly`
  immutables or pure stateless service methods. No singletons exist. This matters because it is the
  compensation Rule 1 depends on — and it holds.

## Suggested task split

The six findings do not belong in one ticket. A defensible split:

| Task | Contents | Why grouped |
| :--- | :--- | :--- |
| **Build & ship configuration** | Findings 1 + 2 | Both are about what CI actually produces; a Build Profile is where the stripping level would be set anyway |
| **Asset import presets** | Finding 3 | Self-contained, cheap, and time-sensitive — the cost grows with every asset added |
| **URP tiers for a 2D game** | Finding 4 | Needs a design decision before any work; may amend the rule instead |
| **Guardrail honesty** | Finding 5 | Documentation and settings only, no Unity work |
| **Configuration validation in CI** | Finding 6 | Depends on the others being decided first |
