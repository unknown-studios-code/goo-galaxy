# C# analysis in a Unity project: replacing `dotnet format` with analyzers Unity runs

**Status:** open — needs refinement into a task
**Trigger:** `dotnet format` deleted a `using` directive during GOOM-6 and caused a compile error. Investigating
that produced the removal recorded below, and left a gap that this document scopes.

---

## What changed already

`check:dotnet` and `format:dotnet` were removed from `package.json`, and `goo-galaxy.slnx` was removed from
version control. Nothing replaced them. This is the debt.

The remaining gates are:

| Tool                  | Scope                                              | Local | CI  |
| :-------------------- | :------------------------------------------------- | :---- | :-- |
| CSharpier             | C# layout — braces, wrapping, `printWidth 160`     | ✅    | ✅  |
| editorconfig-checker  | Indentation, line endings, final newline, line len | ✅    | ✅  |
| Prettier              | JSON, Markdown, YAML                               | ✅    | ✅  |
| **Roslyn code style** | **The 45 `dotnet_naming_rule` entries, IDE0005**   | ❌    | ❌  |

Local and CI now agree exactly, which was the other half of the problem. The cost is the bottom row.

## Why `dotnet format` could not stay

Three independent reasons, in increasing order of severity.

### 1. Its inputs are artifacts Unity owns

`*.csproj` is gitignored, correctly — Unity regenerates every project file whenever an `.asmdef` is added,
renamed, or has its references changed. `goo-galaxy.slnx` was tracked until now, which left the repository in a
state that could not work: the committed solution referenced nine `.csproj` files that `.gitignore` excluded, so
a clean clone never had them. The file also churned in three consecutive feature pull requests (`1086b4d`,
`fb036ac`, `ce699ba`) for no reason other than an assembly appearing.

A quality gate whose input is regenerated by another tool is a gate with no stable contract.

### 2. It is a second compiler over the same code

Unity compiles with its own Roslyn, its own reference set, and its own analyzer versions. `dotnet build` would
be a parallel compilation with different reference resolution. When the two disagree, Unity is authoritative by
definition — it is what produces the game — so the second opinion has no standing.

### 3. In write mode it deletes code, silently

This is the one that actually bit. The failure needs a precise statement, because the obvious explanation is
wrong.

**What happened.** The EditMode assembly was renamed from `GooGalaxy.Runtime.Tests.EditMode` to
`GooGalaxy.Tests.EditMode`. The `.asmdef` and the `[assembly: InternalsVisibleTo(...)]` in `AssemblyInfo.cs`
were both updated. Unity had not re-synced, so on disk the project was still
`GooGalaxy.Runtime.Tests.EditMode.csproj`, declaring the old `AssemblyName`.

Roslyn then asked whether the test assembly could see `Runtime.Board`'s internals. `InternalsVisibleTo` named
`GooGalaxy.Tests.EditMode`; the assembly, per the stale csproj, was `GooGalaxy.Runtime.Tests.EditMode`. Names
differ, so access was denied. `MovementResolver` is `internal`, so every symbol behind
`using GooGalaxy.Runtime.Board.Services;` became invisible, `IDE0005` classified the directive as unnecessary,
and `format:dotnet` removed it. The next Unity compile failed with `CS0103`.

Opening Unity regenerated the csproj from the `.asmdef`, the `AssemblyName` matched `InternalsVisibleTo` again,
and the directive stopped being flagged.

**The explanation that is wrong.** Running with `-v diag` shows
`Project reference found without a corresponding metadata reference` for five projects, which looks like the
culprit. It is not. When a `ProjectReference` points at a project loaded in the same solution, Roslyn links them
through the project graph rather than a compiled DLL; the warning notes the missing binary and analysis proceeds
correctly. `npm run format` ran repeatedly afterwards with Unity in sync and never removed another directive.

**The real risk window** is therefore narrow and specific: **between an `.asmdef` or `AssemblyInfo.cs` edit and
Unity's next re-sync.** That window is exactly where agent-driven work lives, because assembly definitions get
edited with the editor closed.

The asymmetry that settles it: in `--verify-no-changes` mode a stale csproj yields a false *failure*, which
someone notices. In write mode it yields a silent *deletion*, which nobody notices until the compile breaks.

## What should replace it

Unity supports Roslyn analyzers natively. A DLL placed in the project and given the **`RoslynAnalyzer` asset
label** is fed into Unity's own compilation, and can be scoped per assembly through `.asmdef`. Unity reads
`.editorconfig` to configure them.

That inverts every objection above:

- The input is the `.asmdef` graph, which is source, not a regenerated artifact
- There is one compilation, not two, so there is nothing to disagree with
- References are always correct, because it **is** Unity's compilation
- The rules run in the editor as you type, in the CI Unity jobs, and in player builds — the same rules, everywhere
- Nothing runs in write mode, so nothing can delete a `using`

The project currently has no analyzer DLLs and no `.asmdef` referencing one, so this is greenfield.

## Open questions for refinement

1. **Which analyzer package.** The `IDE####` code-style rules — including `IDE1006`, which enforces the naming
   matrix — ship in `Microsoft.CodeAnalysis.CSharp.CodeStyle`. Some of those rules assume the SDK's
   `EnforceCodeStyleInBuild` semantics, which Unity does not set. **This needs a spike before it becomes a
   gate:** confirm the package loads in Unity, that `.editorconfig` naming rules actually fire, and that it
   produces no false positives against the existing codebase.
2. **Warnings or errors.** Analyzer output as warnings is advisory and will be ignored. As errors it blocks
   compilation in the editor, which is disruptive mid-refactor. A middle path is warnings locally and errors in
   CI, which Unity does not express directly.
3. **How CI fails on them.** Unity compile warnings do not fail `game-ci/unity-test-runner` today. Making them
   fail needs either a build step that greps the Unity log or an editor script asserting a clean compile.
4. **Scope.** Runtime assemblies only, or tests as well? Test fixtures deliberately break some conventions
   (long descriptive method names), so a blanket application may need per-`.asmdef` exclusions.
5. **Is `IDE0005` worth recovering at all.** Unused usings are cosmetic, and it was the single rule that caused
   the damage. It may be deliberately left out.
6. **Whether the naming matrix earns this.** 45 `dotnet_naming_rule` entries are currently enforced by review
   alone. If that is judged acceptable, the honest move is to say so in `unity-code-style.md` rather than carry
   a rule nothing checks.
